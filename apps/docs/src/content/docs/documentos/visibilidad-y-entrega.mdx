Todo documento nace **privado**. Publicarlo sirve para compartir un enlace que cualquiera puede abrir. Esta página cubre cómo publicar y despublicar, cómo lee el documento quien lo recibe y las dos formas de entregarlo.

Antes de entregar, el documento tiene que estar `anchored`: ver [Estados y revocación](/documentos/estados-y-revocacion/).

## Publicar o despublicar

Una llamada sin body: el valor (`public` o `private`) va en la URL.

```bash
# publicarlo
curl -s -X PUT -H "Authorization: Bearer $SOVRA_API_KEY" \
  "$BASE_URL/api/v1/issuer/documents/$DOCUMENT_ID/visibility/public"

# y volverlo privado
curl -s -X PUT -H "Authorization: Bearer $SOVRA_API_KEY" \
  "$BASE_URL/api/v1/issuer/documents/$DOCUMENT_ID/visibility/private"
```

Responde `200 OK` con el mismo objeto que [la emisión](/documentos/emitir/#la-respuesta), con `visibility` actualizada. Nada más cambia: el documento no se reemite. En la referencia: [`make-document-public`](/api/make-document-public/) y [`make-document-private`](/api/make-document-private/).

## Qué restringe la visibilidad, y qué no

**La visibilidad restringe el enlace, no el documento.**

- `public`: tener el `id` o el enlace alcanza para leerlo.
- `private`: el enlace solo no alcanza; hace falta sesión del dashboard.

<Aside type="caution" title="Volver a privado no recupera nada">

Un `credential` ya entregado sigue legible y verificable por quien lo tenga, para siempre. Privado significa "el enlace por sí solo no basta", nunca "los bytes son secretos". Para invalidar un documento existe la [revocación](/documentos/estados-y-revocacion/#revocación).

</Aside>

La visibilidad tampoco forma parte del documento: no está cubierta por la firma. Y si construís un buscador o índice que consultan terceros, incluí **solo** documentos `public`: servir un privado por búsqueda anula la decisión del emisor.

## Leer un documento: la zona pública

Quien recibe el documento lo lee con `GET /api/v1/documents/{id}`: **sin `/issuer` y sin API key** ([referencia](/api/documents/retrieve/)).

```bash
curl -s "$BASE_URL/api/v1/documents/$DOCUMENT_ID"
```

- Si es **público**, tener el `id` alcanza.
- Si es **privado**, responde `401 authentication_required`, incluso con una API key. Tu integración lee sus propios documentos con [el listado](/documentos/emitir/#listar-los-documentos-del-workspace).
- Responde con `Access-Control-Allow-Origin: *`, así que se puede llamar directo desde el navegador.

La respuesta trae lo necesario para mostrar y verificar el documento:

| Campo | Qué es |
|---|---|
| `credential` | **El documento en sí.** Lo único verificable de toda la respuesta. |
| `layout` | Cómo dibujar la hoja. Ver [Renderizado](/documentos/renderizado/). |
| `anchor` | `status`, `tx_hash` y `anchored_at` del anclaje. |
| `issuer` | `name`, `did` y `address` del emisor. El nombre es solo informativo. |
| `schema` | El nombre del esquema y la definición de cada campo. |

<Aside type="note" title="Los valores no vienen sueltos">

`schema.claims[]` trae solo las definiciones de los campos. Los valores (el `1234567`, el `"Contenido de Prueba"`) están dentro del `credential`. Ver [Renderizado](/documentos/renderizado/#las-tres-cosas-que-el-json-no-trae).

</Aside>

## Los caminos de entrega

Hay dos formas de hacerle llegar el documento a alguien, y las dos terminan en el mismo `credential`:

| Camino | Qué mandás | Cuándo conviene |
|---|---|---|
| **El string** | El `credential` completo: por correo, en un archivo, en un QR impreso, dentro de un PDF. | Cuando querés que el documento sobreviva a la API. No hace falta que sea público ni que Sovra esté en línea. |
| **El enlace** | `$BASE_URL/api/v1/documents/{id}` | Cuando querés una URL para compartir. Requiere `visibility: "public"`, y quien la abre tiene que [renderizar](/documentos/renderizado/) el JSON. |

- **El QR de una hoja impresa debería llevar el `credential`, no un link.** Así quien lo escanea verifica contra la cadena aunque el servicio ya no exista.
- **Publicar no es autorizar.** El `id` es un UUID v4 y no se adivina, pero si se filtra, el documento se lee.

<Details title="Errores de visibilidad y lectura pública">

| Respuesta | Dónde | Causa |
|---|---|---|
| `401 invalid_api_key` | `PUT …/visibility/…` | Key inválida, o el header no decía literalmente `Bearer`. |
| `422 invalid_visibility` | `PUT …/visibility/…` | El último segmento del path no es `public` ni `private`. |
| `401 authentication_required` | `GET /api/v1/documents/{id}` | El documento es privado y no hay sesión del dashboard (la cookie `document_session` o `Authorization: Bearer` con el token de sesión). Pasa incluso con una API key en el header. No es una falla de tu integración: es la respuesta correcta. |
| `404 document_not_found` | Los dos | Id inexistente, malformado o de otro workspace. No distingue entre los tres casos, a propósito. |

La tabla completa está en [Errores de documentos](/errores/documentos/).

</Details>
